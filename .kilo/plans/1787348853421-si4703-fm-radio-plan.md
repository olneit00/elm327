# Implementierungsplan: Si4703 FM/RDS-Radio für Headunit

## Kontext

Das bestehende `headunit/`-Projekt (ESP32 + GC9A01 240×240 Runddisplay, LVGL 9 + LovyanGFX, analoge Uhr via `ClockScreen`) wird um ein FM/RDS-Radio auf Basis des **Hailege Si4703 RDS FM Radio Tuner Evaluation Breakout Board** erweitert. Die Bedienung erfolgt primär über eine mobile Weboberfläche (iPhone/Safari), zusätzlich soll der Radiozustand später auf dem GC9A01-Display angezeigt werden.

Das `motor-node/`-Projekt existiert separat (ELM327-Emulator mit WiFi AP + BLE + `VehicleState`). Es teilt keine Codebasis mit der Headunit. Beide Projekte laufen auf eigenen ESP32.

## Getroffene Architekturentscheidungen

| Entscheidung | Wahl | Begründung |
|---|---|---|
| Si4703 Library | **PU2CLR SI470X** (MIT) | ESP32-spezifisch, aktive Pflege, vollständige RDS-Unterstützung (PS, RT, Time), gut dokumentierte API |
| Webserver | **ESPAsyncWebServer** (LGPL-3.0) | Nicht-blockierend, SSE + REST in einer Library, parallel zu Display/CAN/RDS lauffähig |
| WLAN-Modus | **AP + STA gleichzeitig** | AP `Opel-Radio` für direkte Smartphone-Bedienung + STA für optionale Heim-WLAN-Funktionen (NTP, OTA) |
| Scan-Strategie | **Schnellscan** | Während Scan nur Frequenz+RSSI+Stereo; RDS-Namen (PS) erst beim aktiven Hören laden |
| Persistenz | **LittleFS + JSON** | Senderliste, Favoriten, letzte Frequenz, Lautstärke, WLAN-STA-Credentials |
| API | **REST + SSE** | REST für Befehle (tune/seek/scan/volume), SSE für Live-Status/RDS-Updates |
| RDS live | **Ja, via SSE** | RadioText und PS werden per SSE an verbundene Browser gepusht |
| Lautstärke | **UI 0–100%, intern 0–15** | Mapping `percent = round(hardware * 100 / 15)` |
| Mono/Stereo | **Nur anzeigen (Auto)** | Si4703 automatische Stereo-Erkennung, keine manuelle Umschaltung |
| RST Pin | **GPIO 4** | Frei, keine Kollision mit SPI (18,23,5,27,33) oder I²C (21,22) |
| Interrupt | **Kein (Polling)** | GPIO2/Interrupt nicht angeschlossen; RDS und Seek-Status per I²C-Polling |
| Display | **RadioScreen als eigene LVGL-Seite** | Neben ClockScreen, Umschaltung später via Bedienelement |
| Audio | **Analog (Klinke am Breakout)** | 3.5mm Buchse am Si4703-Board, später I2S/BT nicht blockiert |
| CAN/GALA | **Vorbereitet** | `RadioService` akzeptiert optionale Geschwindigkeit für GALA; CAN-Integration später |
| UI-Stil | **Klassischer Radio-Look** | Dark Mode, Frequenzskala, Drehregler-Optik, große Touch-Flächen |

## Datenmodell

```cpp
// include/radio/RadioStation.h
struct RadioStation {
    uint16_t frequency;      // 8750 = 87.50 MHz (in 10kHz-Schritten)
    char programService[9];  // RDS PS Name, 0-terminiert, "" wenn unbekannt
    uint8_t rssi;            // 0-255
    bool stereo;             // true=Stereo
    bool favorite;           // Favoriten-Markierung
};

// include/radio/RadioStatus.h
struct RadioStatus {
    RadioState state;        // Off/Idle/Tuning/Seeking/Scanning
    uint16_t frequency;      // aktuelle Frequenz
    char programService[9];  // aktueller PS Name
    char radioText[65];      // aktueller RadioText
    uint8_t rssi;
    bool stereo;
    uint8_t volume;          // 0-15 (Hardware)
    bool muted;
    uint8_t scanProgress;    // 0-100
    uint8_t scanCount;       // gefundene Sender
};
```

Frequenz-Encoder: `uint16_t` in 10kHz-Schritten. 87.50 MHz = 8750, 108.00 MHz = 10800. Bereich: 8750–10800 (Europa/Deutschland).

## Radio-State-Machine

```
States: Off, Idle, Tuning, Seeking, Scanning

Off ──powerOn()──> Idle
Idle ──setFrequency()──> Tuning ──[complete]──> Idle
Idle ──seekUp/Down()──> Seeking ──[found/timeout]──> Idle
Idle ──startScan()──> Scanning ──[progress/complete/cancel]──> Idle
Any ──powerOff()──> Off
```

Alle Übergänge sind nicht-blockierend: `RadioService::loop()` wird aus `main loop()` aufgerufen und macht je nach State einen Schritt, dann zurück. Kein `delay()`, keine `while(waiting)`-Schleifen.

## Scan-State-Machine (Schnellscan)

```
ScanState: Idle → SeekStart → SeekWait → StoreStation → NextSeek → ScanComplete

- SeekStart: Si4703 seekUp() initiieren
- SeekWait: getStatus() pollen (jeden loop-Durchgang), prüfen STC-Bit
- StoreStation: Frequenz+RSSI+Stereo speichern, Duplikatprüfung gegen existing list
- NextSeek: Wenn Frequenz > 10800 oder Wrap → ScanComplete, sonst SeekStart
- ScanComplete: Nach Frequenz sortieren, persistieren, State→Idle
- cancelScan(): ScanState→Idle, Teilergebnis behalten
```

RDS wird während Scans NICHT gesammelt. PS-Namen werden erst beim aktiven Hören (Idle-State) per RDS-Polling aktualisiert und per SSE gepusht.

## RDS-Verarbeitung

- `RadioService::loop()` pollt im `Idle`-State regelmäßig RDS (alle ~40ms einen Block)
- PU2CLR-Library bietet `getRdsReady()`, `getRdsText()`, `getRdsStation()`
- Bei Änderung von PS oder RT: `RadioStatus` aktualisieren → SSE-Event an alle Clients
- RDS-Timeout: Wenn nach 5s kein PS empfangen, zeigt UI `"87.50 MHz"` als Fallback


SSE-Client-Liste wird vom `WebServer` verwaltet. `RadioService` hat einen Callback/Observer, der bei Änderungen alle SSE-Clients benachrichtigt.

## Web-UI-Struktur

Klassischer Radio-Look, Dark Mode (schwarzer Hintergrund, grüne/orange Akzente), responsive, keine externen Ressourcen.

```
/ (oder /radio)         → Senderübersicht (Senderliste + Scan-Button + Volume)
/radio/station          → Senderansicht (PS, Frequenz, RadioText, Volume, Stereo, RSSI)
/radio/favorites        → Favoriten-Liste (Filter auf Senderliste)
/radio/settings         → WLAN-Settings, manuelle Frequenzeingabe
```

Alle HTML/CSS/JS als einzelne String-Konstanten oder LittleFS-Dateien. JavaScript nutzt `fetch()` für REST und `EventSource` für SSE. Keine Reloads bei Statusänderungen.

**Senderübersicht (`/radio`):**
- Liste der gefundenen Sender (PS-Name groß, Frequenz darunter, RadioText falls vorhanden)
- Tap auf Sender → POST tune → Wechsel zu `/radio/station`
- Oben: "Scan" Button (startet Bandscan, zeigt Fortschrittsbalken per SSE)
- Unten: Volume-Slider (0-100%)
- Mute-Button

**Senderansicht (`/radio/station`):**
- Großer PS-Name (RDS, live via SSE aktualisiert)
- Frequenz darunter
- RadioText (2 Zeilen, live via SSE)
- Stereo/Mono Anzeige
- RSSI Balken
- Volume-Slider
- Mute-Button
- Seek Up/Down Buttons
- "Senderliste" Button (zurück zu `/radio`)

## Fehlerfälle

| Fehler | Behandlung |
|---|---|
| Si4703 nicht am I²C-Bus | `RadioService::begin()` returns false, Serial-Error, Radio deaktiviert |
| I²C-Kollision mit anderem Gerät | Separate I²C-Bus-Instanz oder Prüfung der Adressen |
| RDS-Timeout (kein PS nach 5s) | UI zeigt `"87.50 MHz"` als Fallback |
| Scan findet 0 Sender | UI zeigt "Keine Sender gefunden", Scan abbrechbar |
| Scan endlos (Wrap) | Hard-Stop bei 108.00 MHz oder Frequenz≥Startpunkt |
| WLAN-AP startet nicht | Fallback: nur STA, Serial-Fehler |
| LittleFS voll | Serial-Warnung, älteste Stationsdatei überschreiben |
| SSE-Client disconnected | Client aus Liste entfernen, keine Memory-Leaks |
| Volume 0 = Mute | `setVolume(0)` setzt Hardware-Mute, UI zeigt "Muted" |
| Webserver blockiert Display | ESPAsyncWebServer ist nicht-blockierend (Design-Voraussetzung) |

## Risiken

1. **LVGL-Memory**: Aktivierung weiterer Widgets erhöht RAM-Bedarf. 64KB `LV_MEM_SIZE` muss gegen ESP32-DRAM (≈124KB) abgewogen werden. Render-Buffer (19KB) + LVGL-Pool (64KB) + WiFi-Stack + Radio-Strings → Risiko von Heap-Fragmentierung. *Mitigation*: `LV_MEM_SIZE` schrittweise erhöhen, Heap-Fragmentierung via `ESP.getFreeHeap()` überwachen.

2. **I²C-Bus-Sharing**: Si4703 am Standard-I²C (GPIO 21/22). Aktuell kein anderes I²C-Gerät. Wenn später weitere I²C-Geräte hinzukommen, Bus-Konflikte möglich. *Mitigation*: I²C-Adresse dokumentieren (Si4703 = 0x10).

3. **Audio-Ausgang**: Si4703-Breakout hat 3.5mm-Klinke. Für Auto-Anlage später I2S-DAC nötig. Architektur muss `AudioSink`-Abstraktion erlauben. *Mitigation*: RadioService kapselt Audio nicht (nur Tuner-Steuerung); Audio-Pfad später separat.

4. **AP+STA gleichzeitig**: ESP32 kann AP und STA gleichzeitig betreiben, aber nur auf demselben Kanal wie das STA-Netzwerk. Wenn das Heim-WLAN auf Kanal 1 läuft, läuft auch der AP auf Kanal 1. *Mitigation*: Dokumentation, AP-Kanal konfigurierbar.

5. **PU2CLR-Library Updates**: Library ist aktiv entwickelt, API-Änderungen möglich. *Mitigation*: Version in `lib_deps` pinnen (z.B. `pu2clr/SI470X@^1.0.5`).
